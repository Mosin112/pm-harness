PM HarnessFrom a one-line idea to engineering-ready tickets in one sitting.

A harness is everything you build around an AI model so it can do real work reliably: the context it reads, the procedures it follows, the tools it can reach, and the checks it must pass. This one is built for product management. It takes an idea through five steps, and a person approves every step before the next one starts.

Why a harness

Most people use AI like a very fast intern with amnesia

Chat assistants are impressive, but on their own they start from zero every time, can't see your data, and nobody checks their work. A harness fixes that by giving the same model a job description, a filing cabinet, access to the right tools and a supervisor.

How AI is usually used

Chat
  1. Open a chat and paste meeting notes or a rough idea.
  2. Ask for "a PRD for this". The model guesses the format, the users and the goals.
  3. Get a confident, generic document with invented details that sound right.
  4. Copy it into the wiki and rewrite half of it by hand.
  5. Next time, start again from zero. Each PM gets a different result.
✕No company context, so output is generic
✕Can't see customer evidence or real metrics
✕Nobody checks it, so errors reach engineering
✕Forgets everything between conversations

How we use it at Fasset

Harness
  1. Type one line: /pm-harness:one-shot price alerts
  2. It reads our context library (strategy, users, metric definitions, constraints) and pulls real evidence from our meeting notes, chat, support and analytics.
  3. It follows our procedure: concept and job to be done, then testable behaviour trees, then a clickable prototype, then tickets.
  4. It gets checked: five reviewers in fresh contexts critique the concept, and scripts verify the trees, prototype and tickets.
  5. The PM approves each step, and what was learned is saved for next time.
✓Grounded in our goals, users and data
✓Same quality bar for every PM, every time
✓Mistakes caught before engineering sees them
✓Gets better as the context library grows
Agent=Model+Harness

The model is the engine. The harness is the rest of the car: steering, brakes, dashboard and GPS. A great engine with no car goes nowhere. Swapping in a smarter model helps, but most of the difference in day-to-day results comes from the harness.

What's inside

Six parts, each doing one job

Every part is a plain file you can read: Markdown instructions, a small Python checker and a JSON hook. There's no server and no build step.

Context

A filing cabinet the AI reads first

Small, focused files about our company, strategy, users, metric definitions, stakeholders and constraints. An index tells the AI which file to open for which task, so it reads only what it needs.

context/metrics.md → "every number comes from a governed definition"
Skills

Written procedures for repeat work

Each skill is a short instruction manual: when to use it, the steps, the output format and the gate. The AI loads a skill only when the task matches, which keeps it focused and cheap to run.

skills/write-behaviour-trees/SKILL.md
Connectors

Access to the tools we already use

Meeting notes, team chat, support, product analytics, our data warehouse, the issue tracker, the wiki and design files. The AI works from real evidence instead of guessing.

"6 customer calls, 23 support tickets" — not "users want"
Review

Critics who didn't write the draft

Five reviewer agents (engineering, design, risk, executive, customer advocate) each read the concept in a fresh context, so none of them is defending its own work.

blocking · risk · "buy now?" reads as advice
Checks and gates

Machines check form, people check judgement

Scripts verify that trees are testable, that the prototype shows every outcome and that tickets match the trees exactly. Then the PM approves before the next step. Nothing is posted to Jira, Slack or email without approval.

PASS · 16/16 tree outcomes demonstrated
Memory

It remembers what it learned

Each idea's state lives in its own folder, so any session can pick up where the last one stopped. A decision log and approved context updates mean next week's work starts smarter.

decisions/decision-log.md · "revisit if…"
The pipeline

Five steps, five gates, one sitting

The core of the harness is a one-shot pipeline. Each step is a skill that can run on its own; /pm-harness:one-shot runs them in order and stops at every gate.

Before the pipeline

Find what's worth doing

  • synthesize-signals turns calls, tickets and chat into themes with evidence counts.
  • opportunity-brief sizes an idea with governed metrics and a RICE score.
After the pipeline

Ship it and check it worked

  • stakeholder-update drafts a 200-word update that leads with the ask.
  • launch-readout compares real results with the concept's success metrics.
Every day

Keep the PM's week running

  • meeting-prep and meeting-to-decisions handle the work around meetings.
  • update-context saves what was learned, with approval.
Worked example

Everything below was produced by the harness's own skills and passes its own checks. The feature and the evidence are illustrative sample data, so the example can be shared publicly.

work/price-alerts/01-idea.mdstage: ticketsevidence: some

Price alerts

One-liner: Let investors set a price alert on any asset so they hear about the move without watching the chart.

Who it's for: Active retail investors waiting to buy or sell at a specific price.

Evidence (counted and graded)

  • Investors ask to be told when a price is reached (6 customer calls, 23 support tickets, 8 weeks): "I keep the app open all day just to catch the dip."
  • Investors view assets many times a day without trading (product analytics).
  • Some use a separate alerts app, then switch to us to trade (3 calls).

Price alerts · Concept

Job to be done

When I'm waiting for an asset to reach a price I've decided on, I want to be told the moment it gets there, so I can act on my plan without watching the chart all day.

Forces of progress

PushPullAnxietyHabit
Watching the chart all day; missing moves while busyPeace of mind: "the app will tell me"Too many notifications; alerts that fire lateKeeping the app open; a separate alerts app

Success metrics

MetricDefinitionTarget
Alert adoption (primary)% of weekly active investors with an active price alert15% in 8 weeks
Alert-to-action% of triggered alerts followed by opening the asset within 1 hour40%
Notification opt-out (guardrail)% of investors disabling push in a weekno increase

Scope

In: alerts on any asset, one notification per alert, up to 20 active alerts. Not now: percentage-move alerts, recurring alerts, ordering from the notification.

Constraints checked

  • Notifications state facts only, never advice.
  • Only verified investors can set alerts.

Gate 2: a concept can't be approved while any blocking finding is open. Each of these findings became a line in the behaviour trees.

Every line starts with when (an event), while (a state), if (a condition), then or and (an observable outcome). Each outcome becomes a test.


          

          

        

        

          
The tree checker runs before the PM sees the trees. It checks the grammar and flags words a test can't check, such as "should", "properly" or "fast".


$ python3 .pm-harness/pm_check.py trees work/price-alerts/03-trees
PASS  behaviour trees in work/price-alerts/03-trees
  · functional/price-alert-creation: 13 lines, 6 outcomes
  · functional/price-alert-trigger: 12 lines, 6 outcomes
  · journey/set-and-receive-price-alert: 7 lines, 4 outcomes
  0 error(s), 0 warning(s)

          
Here's what it catches on a weak draft:


FAIL  behaviour trees in drafts/
  ✗ :2  top-level lines must start with 'when'
  ✗ :4  nothing may nest under a 'then' line
  ✗ :5  branch 'when something happens' never reaches a 'then' outcome
  ! :3  'should' is hard to test; name the observable result
  ! :3  'properly' is hard to test; name the observable result

Definition of ready

          
  • Trees approved by the PM
  • Every tree outcome shown in the prototype
  • Blocking review findings resolved

The traceability check works in both directions. Every tree outcome must appear in a ticket, and every requirement in a ticket must exist in a tree, so nothing gets lost and nothing gets made up.


$ python3 .pm-harness/pm_check.py tickets work/price-alerts/03-trees work/price-alerts/05-tickets.md
PASS  ticket traceability
  · 16 tree outcomes, 14 outcome lines in tickets
  0 error(s), 0 warning(s)

          
Reword a single line in a ticket and it fails:


FAIL  ticket traceability
  ✗ journey/set-and-receive-price-alert: outcome not in any ticket:
      'then the asset page opens'
  ✗ ticket requirement not found in any tree (invented or reworded):
      'then the asset page opens instantly'

          
Gate 5: nothing is created in the tracker until the PM approves the exact draft.

        

      

    

  






  

    

      
Traceability

      
One line of intent, followed all the way to code

The handoff

      
Where product ends, engineering's harness begins

      
Our engineers already work with their own harness, an internal Claude Code plugin that writes tests before code. It reads behaviour trees in exactly this format. So the PM harness doesn't just hand over a document; it hands over the tests.

How it helps us

      
Faster, without skipping the steps that matter

      
The aim isn't to replace product judgement. The harness takes over the mechanical parts of the job and holds every piece of work to the same standard, so PMs spend their time on decisions and customers.

    

    

      
Speed with the checks kept
Going from idea to engineering-ready used to mean days of drafts, review meetings and rewrites. The pipeline is designed to do it in one working session, with every gate still in place.

      
One quality bar
Every PM's concept has a job statement, counted evidence, defined metrics and a risk check. A new PM produces the same structure as a senior one on day one.

      
Nothing lost in translation
Acceptance criteria are the tree lines, word for word, and a script proves it. Engineers build exactly what was agreed, and edge cases are written down before anyone codes.

      
Risk checked every time
Regulatory and wording constraints live in one file that a dedicated risk reviewer checks on every concept. It's part of the procedure, not something someone has to remember.

      
Evidence over opinion
Claims carry source counts, quotes are real, and every number names its query. A hunch is allowed, but it has to be labelled as one.

      
It compounds
Decisions, context updates and launch readouts feed back into the library, so the harness knows more about our product each month. Improving one skill improves it for every PM.

    

    

      
What stays with people
  • Intent: which problems are worth solving.
  • Approval at every gate, including every write to Jira, Slack or email.
  • Talking to customers. The harness organises evidence; it doesn't replace collecting it.
  • Trade-offs between goals, teams and timing.

      
Limits we plan around
  • Thin evidence stays thin. The harness labels it, but it can't create more of it.
  • Connectors sometimes disconnect. Skills must report a missing source instead of working around it.
  • Long sessions drift. State lives in files, so work resumes cleanly in a fresh session.
  • Context goes stale. The harness flags context files that haven't been updated in 90 days.

Get started

      
Install, set up, run

      
Works in Claude Code and in Claude's desktop app (Cowork). The plugin is plain files, so you can read every instruction before you install it.

    

    

      
1 · Install
Add the plugin
/plugin marketplace add mosin112/pm-harness
/plugin install pm-harness@pm-harness
In Cowork: Customize → Browse plugins → Add marketplace from GitHub → mosin112/pm-harness.

      
2 · Set up
Create your workspace
/pm-harness:setup
Creates the context library and asks short questions to fill it in. It checks your connectors too, and writes nothing to them.

      
3 · Run
Take an idea through
/pm-harness:one-shot price alerts
Or run one step at a time, starting with /pm-harness:capture-idea.
